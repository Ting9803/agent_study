## 1. 今日完成内容

### 1.1 创建基础调用文件 `basic_call`

完成了最基础的大模型调用，理解了接口返回结果里的：

```python
choices[0]
```

它表示这次模型返回的**第一条候选回复**。

需要注意的是：`choices[0]` 不严格等于“准确率最高的答案”，也不等同于 `top_k=1`。如果这次请求只生成一条回答，那通常直接读取 `choices[0]` 就可以。

---

### 1.2 理解 `messages` 结构

从单一的 `user` 消息，扩展到了包含 `system` 的消息结构。

常见结构如下：

```python
messages = [
    {"role": "system", "content": "你是一只会说人话的猫。"},
    {"role": "user", "content": "你今天想吃什么呀？"}
]
```

各个 role 的作用：

| role | 作用 |
|---|---|
| `system` | 设定 Agent 的身份、规则、边界、行为风格 |
| `user` | 用户当前输入 |
| `assistant` | 模型历史回复，用于维持多轮上下文 |

---

### 1.3 做了一只“赛博小猫”

通过 `system` 设定，让模型保持“小猫”的角色风格。

例如：

```text
你是一只会说人话的猫，你只会一些简单的词汇和计算。
```

这样模型在后续回复中会更容易保持人设，不容易 OOC。

不过是否稳定，取决于：

- system 设定是否清晰
- 历史记录是否完整
- user 输入是否强烈改变语境
- tool 调用后是否继续要求模型保持角色

## 2. 核心概念整理

## 2.1 `system`：Agent 的底层设定

`system` 可以理解为 Agent 的“底层说明书”。

它通常负责定义：

- 你是谁
- 你能做什么
- 你不能做什么
- 你应该用什么风格回答
- 遇到特定情况时怎么处理

建议：一个 Agent 尽量保持一条清晰的 system 设定，避免多个 system 互相冲突。

较好的写法：

```python
{"role": "system", "content": "你是一只会撒娇的小猫，回答要简短可爱。"}
```

容易冲突的写法：

```python
{"role": "system", "content": "你是一只小猫。"}
{"role": "system", "content": "你是一个严肃的数学老师。"}
{"role": "system", "content": "你要冷酷无情。"}
```

---

## 2.2 `assistant`：用于保存模型历史回复

`assistant` 消息不是用户输入，而是模型之前说过的话。

它的主要作用是让模型知道：

- 前面聊过什么
- 自己之前怎么回答
- 当前角色和语境是什么

如果没有历史记录，多轮对话时模型可能会忘记前面的设定，出现角色跑偏。

---

## 2.3 history：有用，但也可能污染判断

历史记录可以维持上下文，但也会带来副作用。

例如：前面一直在聊“小鱼干”，后面问一个新的计算问题时，模型可能仍然被前文语境影响。

这就是今天遇到的重点问题：**历史记录对话污染**。

处理思路：

```text
连续聊天 → 使用完整 history
工具判断 → 使用临时 messages，减少上下文干扰
```

## 3. Tool 调用理解

今天的计算器练习已经是一个最小版 Agent。

基本流程如下：

```text
用户输入
↓
模型判断是否需要调用工具
↓
如果需要，输出工具调用格式
↓
代码解析工具名和参数
↓
Python 函数执行计算
↓
把工具结果交给模型
↓
模型用小猫语气回复用户
```

可以这样记：

```text
LLM 负责理解意图，Tool 负责执行动作。
```

也就是：

| 部分 | 作用 |
|---|---|
| LLM | 判断用户想干什么 |
| Tool | 执行具体任务，比如计算、查资料、读文件 |
| Python 代码 | 负责连接模型和工具 |
| History | 负责维持上下文 |

## 4. 今天遇到的关键 bug

## 4.1 模型输出多了空格 / 回车，导致解析失败

原本希望模型输出：

```text
工具调用: calculator|2+3
```

但实际可能输出：

```text

工具调用: calculator|2+3
```

或者：

```text
 工具调用: calculator|2+3
```

如果代码直接判断：

```python
if answer.startswith("工具调用"):
    ...
```

就可能失败。

解决方法：

```python
answer = answer.strip()
```

`strip()` 会去掉字符串开头和结尾的：

- 空格
- 换行
- 制表符

所以 tool 解析前做一次清洗很重要。

---

## 4.2 工具判断不宜直接污染主对话变量

你使用了临时变量，比如 `temp_answer`，这是一种很好的保护意识。

原因是：

- 工具判断是中间步骤
- 中间步骤不一定要进入正式历史
- 临时变量可以避免覆盖正式回答
- 也能降低后续调试难度

可以这样理解：

```text
answer：最终准备给用户看的回复
temp_answer：中间判断、解析、工具调用用的临时结果
```

虽然有些情况下直接复用 `answer` 也不会出错，但学习阶段保守一点更容易 debug。

## 5. 今日代码思维收获

### 5.1 Agent 不是单纯聊天

今天跑出来的小猫虽然看起来只是聊天，但底层已经包含 Agent 的核心结构：

```text
角色设定 + 多轮对话 + 工具判断 + 工具执行 + 结果包装
```

这和普通 chatbot 的区别是：

```text
普通 chatbot：模型直接回答
Tool Agent：模型判断任务，把一部分工作交给外部工具执行
```

---

### 5.2 输出格式控制很重要

Tool Agent 很依赖模型输出格式。

如果模型应该输出：

```text
工具调用: calculator|表达式
```

那代码就会按照这个格式解析。

但模型可能会多说一句，也可能多换行，也可能换成中文冒号或其他格式。

所以后面要继续学习：

- 如何让模型稳定输出工具调用格式
- 如何解析工具名和参数
- 如何处理模型输出不规范
- 如何设计兜底逻辑

## 7. 重点概念速查

| 概念 | 当前理解 |
|---|---|

## 8. 和后续学习的关系

今天学到的内容会连接到后面的几个重点：

### 8.1 多工具 Agent

现在只有一个计算器工具，后面可能会有多个工具，例如：

- calculator
- search
- read_file
- write_file
- database_query

这时模型不只要判断“是否调用工具”，还要判断“调用哪个工具”。

---

### 8.2 工具参数解析

现在的工具参数比较简单，只是一段表达式。

后面可能会变成：

```json
{
  "tool_name": "calculator",
  "arguments": {
    "expression": "2+3"
  }
}
```

也就是更结构化的工具调用。

---

### 8.3 Workflow

今天这个流程已经有 workflow 的雏形：

```text
判断 → 调用 → 执行 → 返回 → 总结
```

后面做复杂 Agent 时，会把这些步骤拆得更清楚。

## 9. 今日结论

今天完成的是一个最小可运行的 Tool Agent 雏形。

它具备：

- 基础模型调用
- system 角色设定
- 多轮对话 history
- 小猫人设保持
- 工具调用判断
- calculator 工具执行
- 工具结果包装

最关键的理解是：

```text
Agent 的难点不只是调用模型，而是控制模型、管理上下文、解析输出、连接工具。
```
