## 3. 今天完成的能力

### 3.1 calculator：继续使用计算工具

示例任务：

```text
昨天吃了 2 个小鱼干，今天可以比昨天多吃一个，所以今天可以吃多少个小鱼干？
```

模型识别到这里需要计算，于是调用 `calculator` 工具。

这个工具的作用是处理明确的数学计算，避免模型自己瞎算或算错。

可以理解为：

```text
模型负责理解题意
calculator 负责执行计算
模型再把结果包装成自然语言回复
```

---

### 3.2 write_file：把内容写入本地文件

示例任务：

```text
你可以写两行诗到 poem.txt 来表达你的心情吗？
```

模型识别到用户不是单纯聊天，而是希望操作本地文件，于是调用 `write_file`。

`write_file` 的作用是：

```text
把指定内容写入指定文件
```

这一步说明 Agent 已经开始影响外部环境，不只是生成文字。

和 calculator 不一样，`write_file` 会产生一个本地状态：

```text
poem.txt 文件被创建或更新
```

这个状态不只存在于聊天记录里，也真实存在于项目文件目录中。

---

### 3.3 read_file：读取本地文件内容

示例任务：

```text
你可以读取出来给我听听你的诗吗？
```

模型需要理解：

```text
用户说的“读取出来”，指的是刚刚写入的 poem.txt
```

然后调用 `read_file` 工具读取文件内容。

这一步比 calculator 更接近真实 Agent，因为它涉及连续任务：

```text
上一轮写入文件
↓
下一轮读取文件
```

这里出现了两种“记忆”：

```text
1. messages 里的聊天历史
2. 本地文件系统里的真实文件
```

模型可以通过聊天历史知道“刚才写过 poem.txt”，但真正能不能读出来，取决于 `write_file` 是否真的写入成功，以及 `read_file` 是否读取的是同一个路径下的文件。

## 4. 今天理解到的关键概念

### 4.1 多工具 Agent

第三天的小猫 Agent 已经不是只会调用一个工具，而是可以根据不同任务选择不同工具。

比如：

```text
计算小鱼干数量 → calculator
写诗到 poem.txt → write_file
读取 poem.txt → read_file
```

这说明 Agent 开始具备基础的“工具路由”能力。

也就是：

```text
模型根据用户意图，判断应该调用哪个工具。
```

---

### 4.2 工具不是只写函数，还要接完整链路

新增一个工具，不是只写一个 Python 函数就结束了。

完整链路包括：

```text
1. 写 Python 工具函数
2. 在 tools 中描述这个工具
3. 确保工具名和 function.name 对得上
4. 解析 function.arguments
5. 根据工具名分发到对应 Python 函数
6. 执行工具
7. 把工具结果用 role="tool" 回填到 messages
8. 再次调用模型生成最终回复
```

漏掉其中任何一步，都可能导致工具无法正常运行。

---

### 4.3 文件工具会产生外部状态

calculator 的结果通常是一次性的：

```text
2 + 3 = 5
```

但 `write_file` 和 `read_file` 会和本地文件系统交互。

这意味着工具执行结果不仅存在于模型对话中，还会落到真实文件里。

所以不能只看模型说：

```text
我已经写好了
```

还要确认：

```text
文件是否真的创建
内容是否真的写入
读取时路径是否一致
```

---

### 4.4 工具结果和最终回复要分清

工具结果是程序层面的结果。

比如：

```text
写入成功
读取成功
文件内容为……
计算结果为……
```

最终回复是模型面向用户说的话。

比如：

```text
喵~ 我已经把诗写到 poem.txt 里啦！
```

两者不能混在一起。

更清晰的流程是：

```text
工具执行 → 得到工具结果
↓
工具结果回填给模型
↓
模型生成符合小猫人设的最终回复
```

这样既能保证工具真的执行，又能保持小猫人设。

---

## 5. 第三天暴露的问题

### 5.1 状态不好时容易改得丢三落四

今天状态不好，注意力容易断，导致写代码时可能漏改配套位置。

多工具 Agent 里尤其容易出现这种情况，因为一个工具要牵涉很多地方：

```text
工具函数
tools 描述
工具名
参数结构
函数分发
结果回填
最终回复
```

以后新增工具时，可以按清单逐项检查，避免只改了一半。

---

### 5.2 多工具时要特别注意工具名一致

工具名至少会出现在几个地方：

```text
tools 里的 function.name
模型返回的 tool_call.function.name
Python 分发逻辑里的判断条件
本地工具函数名或映射表
```

这些名字必须统一。

比如不能出现：

```text
tools 里叫 write_file
代码里判断 write
```

否则模型调用了工具，代码却找不到对应分支。

---

### 5.3 文件读写要注意路径

写文件和读文件必须指向同一个位置。

如果当前运行目录不是自己以为的目录，就可能出现：

```text
写入成功，但读不到
读的是另一个目录下的同名文件
文件名拼错
路径不一致
```

文件工具以后最好明确当前工作目录，或者统一使用固定路径。

---

### 5.4 不能只相信模型说“写好了”

模型说“我已经写好了”，不代表文件一定真的写入成功。

真正可靠的是工具执行结果。

所以在文件操作类 Agent 里，需要关注：

```text
write_file 是否真的执行
是否返回成功信息
read_file 是否真的读到了内容
读取内容是否符合预期
```

---

## 6. 今天的总体代码思路

第三天的代码思路可以整理成：

```text
1. 保留小猫 system 设定
2. 初始化 messages
3. 定义多个工具函数
   - calculator
   - write_file
   - read_file
4. 在 tools 里描述这些工具
5. 用户输入一句话
6. 模型根据 tools 判断是否需要调用工具
7. 如果有 tool_calls：
   - 读取 function.name
   - json.loads(function.arguments)
   - 根据工具名调用对应 Python 函数
   - 得到工具执行结果
   - append role="tool"
   - 再次调用模型生成最终回复
8. 如果没有 tool_calls：
   - 直接输出模型回复
9. 保存本轮结果
10. 进入下一轮 loop
```

更短的版本：

```text
定义工具 → 描述工具 → 模型选择工具 → Python 执行工具 → 工具结果回填 → 模型最终回复 → 继续下一轮
```
